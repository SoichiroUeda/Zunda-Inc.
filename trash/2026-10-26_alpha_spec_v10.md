## 1. アルファ版で確かめたいこと

> 「明日の授業と、今日やることを入れると、**何時までに作業を終えて寝ればいいか**が出て、その時刻に収まるように今日の予定が並ぶ。夜に『あと少し起きていたい』と言うと、**AI が何を削ればいいかを提案してくれる**。」

この一連の体験が、1 台のパソコンの Chrome 上で動けば成功です。見た目のきれいさは問いません。

### 1.1 完成の条件（デモで次の 7 つが動くこと）

| # | 操作 | 期待する結果 |
| --- | --- | --- |
| 1 | 初めて開く | 初期設定画面が出る |
| 2 | 時間割で「火曜 1 限」にチェックし、通学 30 分・準備 30 分・目標睡眠 7 時間で保存 | 月曜の夜に開くと、画面上部に「明日 1 限 → 起床 7:45 → 就寝 0:45 → 限界時刻 0:15」と出る（時刻は 3.1 の計算による） |
| 3 | タスクを 4 つ登録（課題・夕食・風呂・洗濯） | 今の時刻から限界時刻までの間に、タスクが並んだタイムラインが出る |
| 4 | 時間が足りない状態にする（タスクを増やす、または遅い時刻で試す） | 一部のタスクが「短縮版」になり、入りきらないものが「明日に回す」に移る |
| 5 | タスクの完了チェックを押す | 完了の表示になり、タイムラインが作り直される |
| 6 | 「あと少し起きていたい」→「30 分」を選ぶ | AI から 2〜3 個の案が出る |
| 7 | 案を 1 つ選ぶ | 選んだ案のとおりにタスクが短縮・明日送りされ、タイムラインと限界時刻が更新される |

### 1.2 アルファでやらないこと

ログイン、クラウド保存、通知、スマホ実機での動作、夜モード、翌朝の記録、課金、デザインの作り込み。
（通知は Web 版では使えないので、ベータで扱います）

## 3. 機能の仕様

### 3.1 起床時刻と限界時刻の計算（案 A）

**入力（S1 で設定）**

| 項目 | 初期値【仮決め】 |
| --- | --- |
| 時間割（月〜金 × 1〜5 限のどこに授業があるか） | なし |
| 通学時間 | 30 分 |
| 朝の準備時間 | 30 分 |
| 目標の睡眠時間 | 7 時間 |
| 最低限の睡眠時間（AI の案でもこれより短くしない） | 6 時間（決定） |
| 寝る準備の時間 | 30 分 |
| 予定がない日の起床時刻 | 8:00 |

**時限の開始時刻（決定）**（京大の時限）

| 1 限 | 2 限 | 3 限 | 4 限 | 5 限 |
| --- | --- | --- | --- | --- |
| 8:45 | 10:30 | 13:15 | 15:00 | 16:45 |

**計算**

```
明日の最初の予定 ＝ 明日の時間割の最初の授業 と 明日の固定予定（S4 で「明日」を選んで入れたもの）のうち早い方
起床時刻 ＝ 明日の最初の予定 − 通学時間 − 朝の準備時間
  （明日に予定がなければ「予定がない日の起床時刻」）
就寝時刻 ＝ 起床時刻 − 目標の睡眠時間
限界時刻 ＝ 就寝時刻 − 寝る準備の時間
```

**例：** 明日 1 限（8:45）→ 起床 7:45 → 就寝 0:45 → 限界時刻 0:15

**「今日」と「明日」の区切り【仮決め】：** 午前 4:00 で日付が変わるとみなす。たとえば深夜 1:00 に開いた場合は、まだ「前の日の夜」として扱い、「明日」はその日の朝のことになる。

**限界時刻をすでに過ぎている場合：** タイムラインは空にして、「限界時刻を過ぎています。今寝れば ○ 時間 ○ 分眠れます」と表示する。

### 3.2 タスク（案 B：短縮版つき）

| 項目 | 内容 |
| --- | --- |
| 名前 | 必須 |
| 通常の所要時間 | 必須。5 分単位 |
| 短縮版の所要時間 | 必須。0 分〜通常の時間。**0 分は「今日はやらなくてよい（明日に回せる）」の意味** |
| 今日必ずやる | チェックあり／なし。初期値はなし |
| 状態 | 未完了／完了／明日に回す |

**定番タスクのボタン【仮決め】**（押すと名前と時間が入る。保存前に変えてよい）

| タスク | 通常 | 短縮 |
| --- | --- | --- |
| 風呂 | 40 分 | 15 分 |
| 夕食 | 45 分 | 20 分 |
| 洗濯 | 15 分 | 0 分 |
| 洗い物 | 15 分 | 0 分 |
| 課題 | 90 分 | 45 分 |

### 3.3 固定予定

- 固定予定（バイトなど）を S4 で入れる。名前・開始時刻・終了時刻と、「今日／明日」の切り替え（初期値は「今日」）。
- **今日の予定：** 今日のタイムラインに並べる（3.4 の空き時間の計算で除く）。
- **明日の予定：** 明日の起床時刻の計算（3.1）にだけ使う。今日のタイムラインには表示しない。
- 例：明日 7:00 から朝のバイト → 明日の最初の予定は 7:00 になり、起床時刻・限界時刻が早くなる。
- 時間割の授業は、アルファでは「明日の起床時刻の計算」にだけ使う。今日のタイムラインには授業を表示しなくてよい（**開発者の判断で表示してもよい**）。

### 3.4 タイムラインの作り方（いちばん大事なロジック）

**いつ作り直すか：** 画面を開いたとき、タスク・予定を追加・編集・完了したとき、交渉の案を選んだとき。

**並べる対象：** 未完了のタスク。並べる順番は「今日必ずやる」が先、その中は登録した順。

**手順**

```mermaid
flowchart TD
    A[開始時刻＝今の時刻を5分単位に切り上げ] --> B[空き時間＝開始時刻〜限界時刻 から固定予定を除いたもの]
    B --> C[全タスクを通常版で、順番に、入る最初の空き時間に置く]
    C --> D{全部入った?}
    D -- はい --> Z[完成]
    D -- いいえ --> E{通常版のままのタスクが残っている?}
    E -- はい --> F[順番の一番後ろから1つを短縮版に切り替え、最初から置き直す]
    F --> D
    E -- いいえ --> G[「今日必ずやる」でないタスクのうち、順番の一番後ろを「明日に回す」へ]
    G --> H{まだ入らない?}
    H -- はい --> G
    H -- いいえ --> Z
```

**決まり**

- 1 つのタスクを途中で分けて置かない（アルファでは分割しない）。
- 限界時刻を越えて置かない。
- 短縮版が 0 分になったタスクは、置かずに「明日に回す」に入れる。
- 「今日必ずやる」タスクまで入らないときは、それらは置けた分だけ置き、入らなかったものを画面に「入りきりません」と赤字で出す（明日には回さない）。

**例 1（全部入る）：** 今 20:00、限界時刻 23:30、固定予定なし。

| タスク（順番） | 通常 | 短縮 | 結果 |
| --- | --- | --- | --- |
| 課題（今日必ず） | 90 | 45 | 20:00-21:30 |
| 夕食 | 45 | 20 | 21:30-22:15 |
| 風呂 | 40 | 15 | 22:15-22:55 |
| 洗濯 | 15 | 0 | 22:55-23:10 |

**例 2（足りない）：** 今 21:00、限界時刻 23:30（使える時間 150 分）。通常版の合計は 190 分で 40 分足りない。

1. 一番後ろの「洗濯」を短縮版（0 分）に → 合計 175 分。まだ足りない
2. 次の「風呂」を短縮版（15 分）に → 合計 150 分。入る

| タスク | 結果 |
| --- | --- |
| 課題 | 21:00-22:30 |
| 夕食 | 22:30-23:15 |
| 風呂（短縮） | 23:15-23:30 |
| 洗濯 | 明日に回す |

**テストについて：** このロジックは画面とは別の関数にして、上の例 1・例 2 を自動テスト（Dart の `test`）にすること。AI に「この 2 つの例をテストにして」と頼めば作れます。

### 3.5 完了チェック

- 押すと「完了」になり、タイムラインから外れて、画面下に「完了したタスク」として残る。
- もう一度押すと未完了に戻る。
- 完了したらタイムラインを作り直す（残りのタスクが今の時刻から並び直る）。

### 3.6 交渉：「あと少し起きていたい」（案 E・AI を使う）

**流れ**

```mermaid
flowchart TD
    A[S2で「あと少し起きていたい」] --> B[S5：希望の延長を選ぶ 15/30/60分 ＋ 理由を自由入力（空でもよい）]
    B --> C{もともとの空き時間 slack_min が希望以上?}
    C -- はい --> N[AIを呼ばない：「空き時間で過ごす（延長なし）」と「今日は延長しない」を表示]
    C -- いいえ --> D[アプリが今の状況をまとめてAIに送る]
    D --> E{10秒以内に正しい形で返ってきた?}
    E -- はい --> F[アプリが案ごとに延長の分数を計算し、上限を超える案・無効な案を捨てる]
    E -- いいえ --> P[予備の案をアプリが作る]
    F --> G[案と「今日は延長しない」を表示]
    P --> G
    N --> H[ユーザーが案を選ぶ]
    G --> H
    H --> I[アプリが案のとおりにタスクを変更し、限界時刻を延長分だけ遅らせてタイムラインを作り直す]
```

**大事な設計の決め事**

- **AI が決めるのは「どのタスクを短縮・明日送りにするか」と、案の見出し・ひとことの文章だけ。数字（分数・時刻）は AI に書かせず、すべてアプリが計算する。** 試験で、AI は分数の計算を間違えることがわかったため（`docs/prompt_negotiation.md` 0・6 章）。
- 「今日は延長しない」案は、**アプリが必ず追加する**（AI には作らせない）。
- 延長した結果、睡眠時間が「最低限の睡眠時間」を下回る案は表示しない。
- 1 晩に延長できるのは合計 60 分まで（決定）。すでに延長した分を引いた残りを超える案は表示しない。希望の延長の選択肢（15/30/60 分）も、残りを超えるものは選べないようにする。

**アプリが計算すること**

| 項目 | 計算 |
| --- | --- |
| もともとの空き時間 `slack_min` | 今の時刻〜限界時刻のうち、タイムライン（3.4）でタスクも予定も置かれていない時間の合計。タイムライン担当（FT）の処理から出す |
| 削って空く時間 | 案の `changes` ごとに、`shorten` なら「通常 − 短縮版」、`postpone` なら「通常」を足し合わせる |
| 必要な延長 | **max(0, 希望の延長 − slack_min − 削って空く時間)** を 5 分単位に切り上げ |
| 延長後の睡眠時間 | 目標の睡眠時間 − （今晩すでに延長した分 ＋ 必要な延長） |
| 表示する見出し | AI の `title` の後ろに、アプリが「（延長 ○分）」または「（延長なし）」を付ける |

**例：** もともとの空き時間 10 分、希望 45 分、案が「洗濯を明日に回す（15 分）＋風呂を短縮（25 分）」→ 10 ＋ 40 ＝ 50 分空くので、必要な延長は 0 分。

**AI に送る内容（例）**

`can_shorten`・`can_postpone` はアプリが計算して付ける（AI に判断させない）。

- `can_shorten`：status が pending で、0 ＜ 短縮版 ＜ 通常 なら true
- `can_postpone`：status が pending で、「今日必ずやる」でなければ true

```json
{
  "now": "22:10",
  "limit_time": "0:00",
  "bedtime": "0:30",
  "wake_time": "7:30",
  "tomorrow_first": "1限 8:45",
  "target_sleep_min": 420,
  "min_sleep_min": 360,
  "extend_min": 30,
  "slack_min": 0,
  "extended_today_min": 0,
  "reason": "ドラマを最後まで見たい",
  "tasks": [
    {"id": "t1", "name": "課題", "normal_min": 90, "short_min": 45, "must_today": true,  "status": "pending", "can_shorten": true,  "can_postpone": false},
    {"id": "t2", "name": "風呂", "normal_min": 40, "short_min": 15, "must_today": false, "status": "pending", "can_shorten": true,  "can_postpone": true},
    {"id": "t3", "name": "洗濯", "normal_min": 15, "short_min": 0,  "must_today": false, "status": "pending", "can_shorten": false, "can_postpone": true}
  ]
}
```

**AI に返してほしい形（JSON で返させる）**

```json
{
  "message": "少し軽くすれば、就寝時刻を守りながら見られそうです。",
  "options": [
    {
      "title": "風呂をシャワーにする（短縮）",
      "changes": [{"task_id": "t2", "action": "shorten"}]
    },
    {
      "title": "洗濯を明日に回し、風呂もシャワーにする",
      "changes": [{"task_id": "t3", "action": "postpone"}, {"task_id": "t2", "action": "shorten"}]
    }
  ]
}
```

アプリでの表示（上の例では slack_min 0・希望 30 分）：

| 案 | 空く時間 | 必要な延長 | 表示 |
| --- | --- | --- | --- |
| 1 | 25 分 | 5 分 | 風呂をシャワーにする（短縮）（延長 5分） |
| 2 | 40 分 | 0 分 | 洗濯を明日に回し、風呂もシャワーにする（延長なし） |
| アプリが追加 | — | — | 今日は延長しない |

- `action` は `shorten`（短縮版にする）か `postpone`（明日に回す）のどちらか。
- タスクを短縮・明日送りにして空いた時間は、タイムライン上の空き時間として残す（ユーザーが自由に使える時間）。
- **アプリ側で AI の返事を確かめ、次の案は捨てる：** JSON の形が違う／知らない `task_id` がある／`can_shorten` が false のタスクに `shorten`、`can_postpone` が false のタスクに `postpone`／同じ案に同じ `task_id` が 2 回／`changes` が空／計算した延長が上限（最低限の睡眠・1 晩 60 分の残り）を超える。全部捨てたら予備の案を出す。
- **予備の案：** `can_postpone` が true のタスクを、順番の後ろから 1 つずつ明日に回し、「slack_min ＋ 空く時間」が希望の延長以上になったところで止める。延長の分数は上と同じ計算。
- Gemini の「JSON で返す」設定（`responseMimeType: application/json` と、`docs/prompt_negotiation.md` 2 章の回答の形 `responseSchema`）を使う。

**AI の呼び出し方（アルファ）**

- Gemini API を、Dart の `http` パッケージで直接呼ぶ（REST API）。Dart 用の古い公式パッケージは今は勧められていないため。
- モデルは **`gemini-3.5-flash-lite`**（決定）。モデル名は 1 か所の定数にして、変えられるようにしておく（提供終了などで変える可能性があるため）。
- **API キーの扱い**
  - キーはオーナーから個人 LINE で受け取る。受け取ったらすぐ自分のパソコンに保存し、LINE のメッセージは送信取り消しする。
  - 保存先はリポジトリ直下の `dart_defines.json`（`.gitignore` に入れて、GitHub に上がらないようにする）。中身は `{"GEMINI_API_KEY": "受け取ったキー"}`。
  - 実行は `flutter run -d chrome --dart-define-from-file=dart_defines.json`。
  - キーをコードに直接書かない。LINE グループ・GitHub・Issue・スクリーンショット・AI ツールのチャット欄に貼らない。
  - アルファのアプリをインターネットに公開しない（Web 版はビルドするとキーが中に含まれるため）。
- **無料枠で使うときの注意**
  - アルファの API は無料枠で使う。無料枠では、入力した内容が Google のサービス改善に使われることがあるので、**本物の個人情報（自分の実際の予定など）は入れず、テスト用のデータで試す**。
  - 1 日に使える回数に上限がある（全員で共有）。自動で何度も呼ぶ作りにしない。「429」というエラーが出たら上限に達したということなので、時間をおくか LINE で相談する。
- ベータでは、キーをアプリに置かない仕組み（Cloud Functions など）に移す。

**プロンプト（AI への指示文）**

- 指示文・回答の形・テストケース（8 個）と結果は、**`docs/prompt_negotiation.md`**（担当 IH）にある。アプリ担当はそれを読み込んで使う。
- 指示文を直したときは、同じファイルのテストケースを AI Studio でもう一度試し、結果の表を更新する。
- 最低限の睡眠・1 晩の上限・延長の分数の判定は、アプリ側の処理なので、AI のテストではなくアプリの自動テスト（`flutter test`）で確かめる。

### 3.7 保存

- 設定・時間割・予定・タスクは、端末内（ブラウザの保存領域）に保存する。`shared_preferences` パッケージを使えば Web でも動く。
- データの持ち方は 4 章のとおり。JSON にして保存すればよい。
- **保存の処理は 1 か所（例：`lib/storage.dart`）にまとめ、担当者を 1 人に決める。** 各画面（S1〜S4、完了チェック、交渉）はその関数を呼ぶだけにし、画面ごとに保存の処理を書かない。複数人が同じ保存の処理を別々に作ると、作業がぶつかったりデータの形がずれたりするため。
- 保存の担当者は、GitHub の Issue #6 の Assignees で示す（決まるまでは当初の案どおり IT）。

## 4. データの形

**時刻の持ち方【仮決め】：** 「その日の 0:00 からの分数」の整数で持つ。日付をまたぐ時刻は 1440 以上で表す（例：0:15 → 1455）。表示するときだけ「0:15」に直す。こうすると、日付をまたぐ計算で間違えにくい。

| データ | 項目 |
| --- | --- |
| 設定 Settings | 通学時間、朝の準備時間、目標睡眠、最低睡眠、寝る準備の時間、予定がない日の起床時刻 |
| 時間割 TimetableEntry | 曜日（1=月〜5=金）、時限（1〜5） |
| 固定予定 FixedEvent | id、名前、日付、開始、終了 |
| タスク Task | id、名前、通常の時間、短縮版の時間、今日必ずやる、状態（未完了／完了／明日に回す）、登録順、短縮版を使っているか |
| タイムラインの 1 行 TimelineItem | 種類（タスク／予定）、元の id、開始、終了、短縮版か |
| 交渉の記録 Negotiation | 日付、延長した分数（その晩の合計を超えないように使う） |

名前の付け方・ファイルの分け方は **開発者の判断でよい**。最初に担当者がこの表をコードにして、全員がそれを使う。

### 5.1 Git の決め事

1. `main` に直接 push しない。作業ごとにブランチを作る（例：`it/input-screen`）。
2. できたら Pull Request を出し、誰か 1 人に見てもらってからまとめる（技術の相談役 FT が中心。手が空いている人でもよい）。
3. Pull Request は小さく。1 つの画面や 1 つの機能ごと。
4. API キーなどの秘密は絶対にコミットしない。
5. 困ったら、自分の AI ツールに「このエラーを初心者向けに説明して」と聞いてから、それでもだめなら LINE で相談。

## 7. 開発者の判断に任せること・迷ったときの原則

**任せること：** 画面の配置・色・ボタンの文言、ファイルの分け方、変数名、使うパッケージ（無料のもの）、状態管理の方法。

**迷ったときの原則（上から優先）**

1. **限界時刻は越えない。睡眠時間を削る提案はしない**（最低限の睡眠時間は絶対に守る）
2. 動くことを優先し、見た目は後回し
3. 仕様書に書いていない細かい部分は、自分で決めてよい。決めたことは Pull Request の説明に一言書く
4. 仕様の意図がわからないとき（何を作るか）→ オーナーに聞く。作り方がわからないとき → FT に聞く
