## 1. プロジェクト概要

| 項目 | 内容 |
| --- | --- |
| プロジェクト名 | 睡眠死守型タスク管理アプリの開発と普及（アプリ名：Rism・仮称） |
| コンセプト | 「睡眠を死守する」オーダーメイド型 AI タスク管理アプリ |
| 初期ターゲット | 「気づいたら深夜2時」になりがちな**大学生** |
| 運営 | 京都大学マーケティング研究所（京大マーケ） / オーナー：ぷらぐら |
| 期間 | 2026年12月末まで（約3ヶ月） |
| 進め方 | ① 1週間のアルファ版トライアル → ② 正式メンバー決定 → ③ 12月の完成に向けて開発・ベータテスト |
| 活動ペース | 週あたり数時間以下（自分のペースで無理なく） |

### 1.1 解決したい課題

- 深夜のスマホ・ダラダラによって就寝時刻が後ろにずれていく。
- 根性論ではなく、**AI × 時間管理の仕組み**で「決めた時間にスッとベッドに入れる」状態をつくる。
- アプリの役割はあくまで**時間・タスク管理**。その結果として就寝時刻を守る。

### 1.2 京大マーケでやる意味

- アイデアを形にするだけでなく、料金プラン設計・ユーザーテスト・マーケティング検証まで、**ビジネスのリアルを実践形式で学べる**。
- 部員自身がターゲット（大学生）なので、部内ベータで実際の行動データを集められる。

### 1.3 開発方針

- **Vibe Coding**（Claude Code 等の AI と対話しながら開発）で、高速・低コストに作る。
- まず「動くもの」を最優先し、部内ベータで検証しながら機能を足していく。

## 2. 機能構想（全体像）

全部を12月までに作るわけではありません。どこまで作るかは [4. 開発フェーズとスコープ](#4-開発フェーズとスコープ) を参照。

### ① AI タイムライン自動最適化【コア機能】

- **固定予定 × タスクのパズル化**：授業・バイトなどの「固定予定」と、やりたい「タスク」（所要時間つき）を登録すると、空き時間を埋めたタイムラインを自動生成する。
- **限界時刻（Bedtime Lock）の提示**：起床時刻と必要な睡眠時間から逆算し、「作業を終えてスマホを置くべき時刻」を表示する。
- **睡眠時間の確保を最優先**に調整する（睡眠の質を上げる要素も考慮）。

### ② AI との対話による微調整

- **対話で修正**：「今日しんどいから緩めにして」「15分でできることある？」などの自然な文章でタイムラインを直す。
- **巻き返し提案**：予定が押したとき、「風呂をシャワーにして15分短縮」「このタスクは明日に回す」などの代替案を出す。
- **前倒し・後ろ倒し**：タスク単位で前後に動かせる。

### ③ 通知・スマホいじり防止

- **限界時刻の通知**：限界時刻が近づいたらローカル通知。
- **タスク開始前通知**：タスク開始の 1 時間〜30 分前に通知。
- **スマホいじり検知**：夜間に画面オンが続いたら「いじってて大丈夫？」と表示する。
  - ※ iOS は他アプリの利用状況の取得に強い制約がある（Screen Time API は特別な許可が必要）。実現方法は要調査・難易度高。

### ④ 学習・フィードバック

- **初回の所要時間計測**：使い始めに、実際にタスクにかかる時間を計測して初期値にする。
- **翌朝の目覚めフィードバック**：「スッキリ起きられたか？」を 3 段階で評価し、疲れが残っていれば翌日のタスク所要時間にゆとりを足す。

### ⑤ 入力の手軽さ・連携

- **定番タスクのクイック追加**：ボタンで「洗濯・洗い物・風呂・食事」などの候補を出してすぐ追加。
- **外部カレンダー連携**（Google Calendar 等）：審査・セキュリティ対応のコストがかかるため後回し候補。

## 3. 収益モデルの方針

### 3.1 決まっていること

- **フリーミアム**（無料プラン＋有料プラン）。
- **無料プラン**：AI 呼び出しに制限あり（＝その日一日分のスケジュール作成まで）。
- **有料プラン**：一週間・一ヶ月などの長期タスク管理、他アプリ連携、AI 呼び出し上限の解放など。
- **京大マーケ部員はプライベートベータ期間中のみ無料**。正式リリース後は一般ユーザーと同じ扱い。
- 「限定コミュニティ連携」は後回し。

### 3.2 マーケティング担当が設計すること

プランの数・価格・内容は**マーケティング担当が設計**します。その際の観点：

1. **API 利用料とユーザー課金額のバランス**：1ユーザーあたりの AI コストが、そのプランの売上（手数料差し引き後）を上回らないこと。
2. **AI モデルの選定**：安価なモデルを前提に、コスパのよいモデルを改めて調査する。上位プランだけ高性能モデルにする必要があるかも含めて検討。
3. **ストア手数料**：アプリ内課金は App Store / Google Play の手数料（小規模事業者は 15% が目安）が引かれる前提で計算する。
4. **広告収益**：無料プランに広告を入れた場合にどれだけ見込めるか。

**1ユーザーあたり AI コストの概算式（例）**

```
月額AIコスト ≒ 1日あたりAI呼び出し回数 × 30日
              × (入力トークン数 × 入力単価 + 出力トークン数 × 出力単価)
```

タイムラインの骨組みはプログラムで作り、AI は「微調整の指示」のときだけ呼ぶ設計（5章）なので、呼び出し回数は少なく抑えられる見込みです。

### 3.3 これまで出たプラン案（検討材料）

| | 案A | 案B |
| --- | --- | --- |
| 無料 | 基本タスク管理・簡易タイムライン（AI制限あり） | 回数制限厳しめ・広告あり |
| 中位 | 月額 500 円：AI 微調整・巻き返し提案フル活用 | 月額 500 円／月額 1,000 円で回数 2 倍 |
| 上位 | 月額 2,000 円：専属 AI アシスタント、行動ログ詳細分析 | 月額 2,000 円：無制限（上位モデル案あり） |

## 4. 開発フェーズとスコープ

### 4.1 アルファ版（1週間トライアル）

**目的：** 「タスクを入れると、就寝時刻を守るタイムラインが出てきて、AIに話しかけると直る」というコア体験が動くことを確認する。機能はかなり絞る。

| 区分 | 内容 |
| --- | --- |
| **必須** | ① 固定予定・タスク（名前・所要時間）の入力（端末内に保存）<br>② 起床時刻・睡眠時間から限界時刻を逆算し、空き時間にタスクを並べたタイムラインを表示（プログラムのルールで生成、AI 不要）<br>③ テキストで調整を頼むと Gemini 等の AI がタイムラインを組み直す（1機能のみ）<br>④ タスクの完了チェック |
| できれば | 限界時刻のローカル通知（Android のみで可）、タスクの編集・削除 |
| やらない | ログイン、クラウド保存（Firestore）、iOS ビルド、課金、スマホいじり検知、翌朝フィードバック |
| 動かす環境 | Flutter で **Android（実機/エミュレータ）または Web（Chrome）**。→ Mac がなくても参加できる |

### 4.2 ベータ版（11月開発 → 12月部内テスト）の候補

優先度は正式メンバー決定後に決める。

- ログイン（Google / Apple）、クラウド保存（Firebase）
- iOS 対応、テスト配布（TestFlight / Firebase App Distribution）
- 限界時刻・タスク開始前のプッシュ通知
- 翌朝の目覚めフィードバック、定番タスクのクイック追加
- 行動データ（就寝時刻など）の記録 ← ベータテストの検証に必須
- AI の API キーをアプリに直接置かない構成（Cloud Functions 経由など）

### 4.3 12月以降に回すもの

- 外部カレンダー連携、高度なスマホいじり検知、アプリ内課金、長期タスク管理、限定コミュニティ

## 5. 技術スタック

| 項目 | 内容 |
| --- | --- |
| アプリ | Flutter（iOS / Android 両対応。アルファは Android / Web で動作確認） |
| バックエンド・DB | Firebase（Authentication / Cloud Firestore）※ベータから |
| AI モデル | 安価なモデルを使う（Gemini 2.5 Flash などが候補。最終決定はマーケ担当のコスト試算を踏まえて） |
| 開発ツール | Claude Code, VS Code, Cursor |
| 開発 OS | アルファは不問。iOS ビルドには Mac（Xcode）が必要なので、ベータでは Mac を持つ人が iOS 担当 |

**ハイブリッド構成：** タイムラインの骨組みはプログラムで生成し、ユーザーが微調整を指示したときだけ AI を呼び出す。API コストを最小化するため。

## 7. 体制・役割分担

各役割とも複数名が参加予定。人数は募集資料に従い固定しません。

| 役割 | 主な仕事 |
| --- | --- |
| リーダー / オーナー（ぷらぐら） | 意思決定・全体総括、仕事の割り振り・進捗管理 |
| 開発責任者 | 開発の進め方・分担を決める、環境構築手順の整備、コードの取りまとめ |
| 開発者 | Claude Code 等を使った Flutter / Firebase 実装、AI 連携 |
| UX/UI リサーチャー | **開発者と連携して画面デザインを考える**、操作の流れ・通知の出し方と文言の設計 |
| マーケティング担当者 | **データ分析**、ベータテスト設計・フィードバック収集、**料金プラン設計**（API 利用料と課金額のバランス）、**AI モデル選定を含むコスト概算**、広告収益の見込み |

- 機能や料金のアイデア出し（ビジネスデザイン）は、役割に関係なく**全員で**行う。最終的な料金プランはマーケティング担当が設計する。

### 7.1 アルファ週の各役割の成果物

| 役割 | 1週間で出すもの |
| --- | --- |
| 開発 | 4.1 の必須機能が動くアプリ（デモできる状態） |
| UX/UI | 主要 2〜3 画面のラフ（手書き・Figma 可）、通知文言案 |
| マーケティング | AI モデル候補の料金比較と 1 ユーザーあたりコストの試算、ベータで測る指標の案、部員数名への睡眠習慣ヒアリング |

### 7.2 開発メンバーの経験について

- 開発者は経験不問のままでよいが、**開発責任者（少なくとも1名）は経験者が望ましい**。1週間という短期間では、環境構築・エラー対応・Git の取りまとめで詰まると全体が止まるため。
- 経験はアンケート（`dev_survey.md`）で確認し、その結果で開発責任者と分担を決める。
